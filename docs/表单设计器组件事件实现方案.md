# 表单设计器组件事件实现方案

## 1. 实现目标

根据《表单设计器组件支持事件清单》和当前组件实现，建立统一的组件事件体系，使表单设计器能够为不同组件配置前端或后端插件函数。

方案需要满足以下目标：

- 支持输入、选择、日期、上传、子表单等组件的标准事件；
- 设计器只展示当前组件实际支持的事件；
- 统一事件参数、插件调用和结果回填方式；
- 区分用户操作、初始化赋值和插件回填；
- 兼容现有 `method.input` 字段脚本；
- 避免同一次值修改重复触发和字段联动循环；
- 复用现有表单事件的插件函数执行能力。

## 2. 当前实现分析

### 2.1 字段值监听

`showItem.vue` 当前通过深度监听 `comDes.props.value` 执行字段输入脚本，并调用 `filterData` 同步表单数据。

该方式存在以下问题：

- 无法区分 `input`、`change`、`focus`、`blur` 等具体交互；
- 用户输入、初始化赋值、公式计算和插件回填会进入同一监听器；
- 数组和对象的深层修改也会触发监听；
- 字段组件显式绑定 `change` 后可能与深度监听重复执行；
- 当前代码仍直接使用 `eval` 执行脚本。

### 2.2 字段组件事件

基础组件大多直接通过 `v-model` 修改 `comDes.props.value`，没有向上层统一转发 Arco 原生事件。

例如：

- `qInput.vue` 仅绑定 `v-model`；
- `qTextarea.vue` 绑定了 `input`，但处理函数为空；
- `qInputNumber.vue`、`qSelect.vue` 和日期组件虽然绑定了 `change`，但主要逻辑已经被注释；
- `qUpload.vue` 自行处理上传和预览，没有统一上报上传成功、失败等事件；
- 子表单、签名、关联查询等业务组件拥有自己的业务处理逻辑，尚未形成统一事件协议。

### 2.3 表单事件执行器

`useFormEvents.ts` 已经具备以下能力：

- 根据事件配置选择插件函数；
- 区分前端和后端插件；
- 生成插件输入参数；
- 获取并缓存前端插件详情；
- 设置函数执行超时；
- 调用后端插件接口；
- 根据输出映射更新表单字段。

但当前只支持整个表单的 `change` 和 `submit`，尚未支持具体字段和具体组件事件。

## 3. 总体架构

组件事件采用“字段组件上报、`showItem` 桥接、公共运行时执行”的结构。

```text
字段组件 qInput/qSelect/qUpload/...
        │
        │ emit('field-event', payload)
        ▼
showItem.vue
  - 判断设计态和数据加载状态
  - 同步字段值到表单模型
  - 补充字段、表单和子表单上下文
        │
        ▼
useComponentEvents
  - 查找字段事件配置
  - 处理防抖、并发和循环保护
  - 调用公共事件执行器
        │
        ▼
eventExecutor
  - 执行前端或后端插件函数
  - 处理输入和输出映射
  - 更新表单模型和 formList
```

### 3.1 组件职责

| 模块 | 职责 |
| --- | --- |
| 字段组件 | 监听底层组件事件，并上报标准化事件 |
| `showItem.vue` | 作为字段事件边界，补充上下文并转发事件 |
| 事件注册表 | 定义不同组件支持的事件及展示信息 |
| `useComponentEvents` | 匹配组件事件配置并控制执行过程 |
| 公共事件执行器 | 执行插件函数以及输入、输出映射 |
| 设计器事件面板 | 展示事件并编辑插件函数配置 |


### 4.3 运行时事件参数

```ts
export interface ComponentEventPayload<T = unknown> {
  name: ComponentEventName | BusinessComponentEventName
  fieldId: string
  fieldType: string
  value?: T
  oldValue?: T
  args?: unknown[]
  source: 'user' | 'programmatic'
  rowContext?: {
    subformId: string
    rowIndex: number
    fieldId: string
    rowData?: Record<string, unknown>
  }
  timestamp: number
}
```

`source` 用于区分：

- `user`：用户直接操作组件；
- `programmatic`：初始化、公式计算、数据联动或插件输出回填。

原生 DOM 事件不直接序列化传给后端。需要将其转换为可序列化的信息，例如：

```ts
{
  type: event.type,
  key: keyboardEvent.key,
  checked: inputElement.checked
}
```

## 6. 字段组件改造

### 6.1 统一事件出口

字段组件统一声明一个 `fieldEvent`：

```ts
const emit = defineEmits<{
  fieldEvent: [payload: {
    name: ComponentEventName | BusinessComponentEventName
    value?: unknown
    args?: unknown[]
  }]
}>()
```

可增加公共方法减少重复代码：

```ts
function emitFieldEvent(
  name: ComponentEventName,
  value?: unknown,
  ...args: unknown[]
) {
  emit('fieldEvent', {
    name,
    value,
    args,
  })
}
```

### 6.2 输入类组件

`qInput.vue` 示例：

```vue
<a-input
  v-model="comDes.props.value"
  :allow-clear="comDes.props.allowClear"
  :placeholder="comDes.props.placeholder"
  :readonly="comDes.props.readonly"
  :disabled="comDes.props.disabled"
  @input="emitFieldEvent('component.input', $event)"
  @change="emitFieldEvent('component.change', $event)"
  @focus="emitFieldEvent('component.focus', comDes.props.value, $event)"
  @blur="emitFieldEvent('component.blur', comDes.props.value, $event)"
  @clear="emitFieldEvent('component.clear', undefined, $event)"
  @press-enter="emitFieldEvent('component.pressEnter', comDes.props.value, $event)"
/>
```

`qTextarea.vue` 和 `qInputNumber.vue` 使用相同方式接入各自支持的事件。

### 6.3 选择类组件

`qSelect.vue` 需要转发：

- `change`
- `clear`
- `remove`
- `search`
- `popup-visible-change`
- `dropdown-reach-bottom`
- `exceed-limit`

单选和多选复用同一个组件时，通过 `comDes.type` 判断是否开放 `remove` 和 `exceedLimit`。

### 6.4 日期和时间组件

日期、日期范围、时间和时间范围组件需要转发：

- `change`
- `select`
- `ok`
- `clear`
- `popup-visible-change`
- `select-shortcut`

事件参数应同时包含组件当前保存的格式化值和 Arco 回调参数。

### 6.5 上传组件

`qUpload.vue` 需要在当前业务逻辑的关键节点主动发出：

```ts
emitFieldEvent('component.uploadProgress', fileInfo, progressEvent)
emitFieldEvent('component.uploadSuccess', uploadedFile)
emitFieldEvent('component.uploadError', fileItem, error)
emitFieldEvent('component.preview', fileItem)
```

删除文件前事件需要支持异步结果：

```ts
const allowed = await dispatchCancelableEvent(
  'component.beforeRemove',
  file,
)

if (!allowed) return false
return !file.example
```

### 6.6 业务组件

业务组件在业务操作发生的位置主动发出事件：

| 组件 | 业务事件 |
| --- | --- |
| 子表单 | 新增行、删除行前、删除行后、子字段修改、排序完成 |
| 签名 | 打开签名、签名完成、重新签名、清除签名 |
| 关联查询 | 查询前、查询成功、查询失败、查询结果修改 |
| 按钮 | 点击、请求前、请求成功、请求失败 |
| 人员/部门 | 打开、确认、取消、清空、移除选项 |
| 地址 | 省修改、市修改、区县修改、详细地址输入、整体修改 |

## 7. `showItem.vue` 改造

`showItem` 中两处动态组件统一监听：

```vue
<component
  :is="comDes.component"
  :com-des="comDes"
  :form-confs="formConfs"
  @field-event="handleFieldEvent"
/>
```

标准处理流程：

```ts
async function handleFieldEvent(payload: FieldEventPayload) {
  if (props.showEdit) return
  if (isDataLoading.value) return

  if (payload.name === 'component.change') {
    provideState?.filterData?.(props.comDes)
  }

  await dispatchComponentEvent({
    ...payload,
    fieldId: props.comDes.id,
    fieldType: props.comDes.type,
    value: payload.value ?? props.comDes.props.value,
    source: 'user',
    timestamp: Date.now(),
  })
}
```

`showItem` 负责：

1. 屏蔽设计态事件；
2. 屏蔽数据初始化阶段事件；
3. 在 `change` 事件执行前同步表单数据；
4. 补充字段信息；
5. 补充子表单行信息；
6. 转发给组件事件运行时；
7. 隔离插件执行异常，避免影响组件基础输入。

## 8. 组件事件运行时

新增：

```text
src/composables/useComponentEvents.ts
```

主要接口：

```ts
export function useComponentEvents(
  form: Ref<Record<string, unknown>>,
  formConfs: Ref<Record<string, unknown>>,
  options?: ComponentEventRuntimeOptions,
) {
  async function dispatchComponentEvent(payload: ComponentEventPayload) {
    // 查找字段事件配置
    // 执行防抖和并发控制
    // 生成插件上下文
    // 调用公共执行器
  }

  return {
    dispatchComponentEvent,
  }
}
```

建议通过 `provide/inject` 将运行时提供给所有 `showItem`：

```ts
export const formEventRuntimeKey =
  Symbol('formEventRuntime') as InjectionKey<FormEventRuntime>
```

这样字段组件和 `showItem` 不需要直接依赖具体页面，也不需要直接调用插件接口。

需要检查所有使用 `showItem` 的运行页面，确保都提供运行时，包括：

- 应用填写页面；
- 表单管理页面；
- 游客填写页面；
- 流程中心填写和修改页面；
- 任务填写页面；
- 表单预览页面；
- 审批详情页面。

设计器编辑态可以提供空运行时，或由 `showItem` 根据 `showEdit` 直接阻止执行。

## 9. 公共事件执行器

将 `useFormEvents.ts` 中的公共能力抽取到：

```text
src/composables/formEvents/
├── eventTypes.ts
├── eventExecutor.ts
├── eventMapping.ts
├── useFormEvents.ts
└── useComponentEvents.ts
```

### 9.1 `eventExecutor.ts`

负责：

- 判断前端或后端插件类型；
- 获取和缓存插件详情；
- 校验必填输入参数；
- 执行前端函数；
- 调用后端函数；
- 超时控制；
- 标准化函数返回值；
- 统一错误信息。

### 9.2 `eventMapping.ts`

负责：

- 普通字段输入映射；
- `$event` 上下文映射；
- 子表单行字段映射；
- 插件输出字段映射；
- 同时更新 `form` 和 `formConfs.formList`。

### 9.3 前端函数上下文

建议提供：

```ts
interface ComponentFunctionContext {
  event: Readonly<ComponentEventPayload>
  field: Readonly<Record<string, unknown>>
  form: Readonly<Record<string, unknown>>
  formConfs: Readonly<Record<string, unknown>>
  getFieldValue: (fieldId: string) => unknown
  setFieldValue: (fieldId: string, value: unknown) => void
  setFieldVisible: (fieldId: string, visible: boolean) => void
  setFieldError: (fieldId: string, message: string) => void
  clearFieldError: (fieldId: string) => void
  utils: {
    callBackend: (...args: unknown[]) => Promise<unknown>
  }
}
```

不再新增直接 `eval` 调用。旧字段脚本继续通过 `executeFieldScript` 兼容执行。

## 11. 旧配置兼容

现有表单使用：

```ts
method: {
  input: string
}
```

兼容规则：

1. 字段没有新的 `component.change` 配置时，值变化继续执行 `method.input`；
2. 字段配置了新的 `component.change` 后，不再重复执行旧 `method.input`；
3. 保存旧表单时不自动删除 `method.input`；
4. 设计器可以提示将旧脚本迁移为“值修改时”事件；
5. 迁移前继续保留旧脚本的 `provideState`、`props` 和 `context`；
6. 新代码统一使用 `executeFieldScript`，不再直接执行 `eval`。

可以在后续版本提供一次性迁移：

```ts
method.input
  └── componentEvents[
        {
          event: 'component.change',
          handlerType: 'legacyScript',
          script: method.input
        }
      ]
```

## 12. 防重复、并发和循环处理

### 12.1 防重复触发

字段组件显式发出 `component.change` 后，需要记录本次变更来源，避免 `showItem` 深度监听再次执行相同事件。

建议将深度监听逐步降级为：

- 旧组件兼容；
- 程序赋值同步；
- 旧 `method.input` 执行。

新组件事件只通过 `field-event` 触发。

### 12.2 防抖和节流

| 事件 | 默认策略 |
| --- | --- |
| `component.input` | 防抖 300ms |
| `component.search` | 防抖 300ms |
| `component.uploadProgress` | 节流 200ms |
| `component.change` | 不防抖 |
| `component.focus/blur` | 不防抖 |

设计器允许覆盖默认防抖时间。

### 12.3 异步竞态

连续输入或搜索触发多个请求时：

- 使用执行序号判断结果是否过期；或
- 使用 `AbortController` 取消旧请求。

只允许最后一次有效请求更新表单。

### 12.4 循环保护

插件输出回填字段时标记：

```ts
source: 'programmatic'
```

默认不因为程序回填再次执行组件插件事件。

如果业务明确需要级联执行，可以在事件配置中增加：

```ts
triggerOnProgrammaticChange: true
```

同时维护执行链 ID 和最大执行深度，避免 A 字段更新 B、B 又更新 A。

### 12.5 可取消事件

以下前置事件允许插件返回 `false`：

- 删除文件前；
- 删除子表单行前；
- 关联查询前；
- 按钮请求前。

多个处理函数中任意一个返回 `false`，后续业务操作终止。

## 13. 错误处理

事件执行失败时应记录：

- 表单 ID；
- 字段 ID 和字段名称；
- 组件类型；
- 事件名称；
- 插件函数 ID；
- 执行链 ID；
- 错误信息。

普通后置事件默认采用 `continue`：

- 展示错误提示；
- 不阻止字段值修改；
- 后续事件可以继续执行。

前置事件可采用 `stop`：

- 停止后续函数；
- 阻止对应业务操作。

组件卸载时需要清理：

- 防抖定时器；
- 节流定时器；
- 未完成请求；
- 事件执行状态。

## 15. 测试方案

### 15.1 单元测试

测试内容：

- 不同组件类型返回正确的事件列表；
- 事件配置匹配正确；
- `$event.value` 等上下文映射正确；
- 输出同时更新 `form` 和 `formList`；
- 防抖、节流和过期结果处理正确；
- 程序回填不会触发循环；
- 可取消事件返回 `false` 时能阻止操作；
- 单个事件执行失败不会破坏基础输入。

### 15.2 组件测试

## 16. 验收标准

满足以下条件后可以认为组件事件能力完成：

1. 一次用户修改只触发一次 `component.change`；
2. 数据初始化和详情回显不触发用户事件；
3. `input` 和 `change` 可以分别配置；
4. 事件面板只显示当前组件支持的事件；
5. 前端和后端插件函数均可执行；
6. 事件参数能够访问当前字段值、旧值和表单数据；
7. 输出映射能够正确回填字段；
8. 插件回填不会产生无限循环；
9. 子表单事件能够携带行号和行数据；
10. 上传事件能够准确反映成功、失败、预览和删除；
11. 设计态不会执行生产插件；
12. 旧表单的 `method.input` 行为保持兼容；
13. 插件执行异常不会阻断组件基础输入；
14. 页面卸载后不存在遗留定时器和请求。
