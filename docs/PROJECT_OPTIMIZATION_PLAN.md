## 2. 待优化事项

### P0：动态配置解析与结构校验

表单、流程、连接器和任务页面仍直接解析后端或本地存储中的 JSON。当前代码快照中有约 314 处 `JSON.parse`，其中包含用于深拷贝的写法，不能机械替换；真正需要治理的是外部配置和历史数据入口。

优先范围：

- `views/application/visitor.vue`、`index.vue`、`manager.vue` 的表单、流程、草稿和原始数据配置。
- `views/doCenterDes/index.vue`、`views/taskFillCenter/` 的流程详情及填报配置。
- `views/flowPath/`、连接器场景和 WebHook 映射配置。
- `composables/useFormEvents.ts` 等事件配置入口。

实施要求：

- 复用 `src/utils/safeJson.ts`，按对象、数组和标量分别提供默认值。
- 解析后校验关键结构；在 `.map`、`.filter`、解构前先归一化可选集合。
- 解析失败记录配置类型和业务 ID，不记录令牌、表单敏感值或完整响应。
- `JSON.parse(JSON.stringify(...))` 的替换单独评估浏览器兼容性，不与容错治理混做。

验收：空值、非法 JSON、旧配置和字段缺失不会导致页面白屏或 `undefined.map`；正常历史配置行为保持不变。

### P0：统一表单提交序列化

提交规则集中在 `src/utils/form.ts`，但应用填报、访客填报、审批详情、任务填报和原始数据编辑存在多个调用入口。栅格遍历已修复，仍需把字段可见性和值转换从页面约定收敛为可测试规则。

必须覆盖：

- 隐藏字段无值时不提交，已有值时按既有业务规则处理。
- 数字、金额空值保持空，不自动变成 `0` 或 `0.00`。
- 日期、时间和日期范围按组件 `value-format` 归一化，并按格式精度补齐缺失部分。
- 人员/部门单选、多选保持后端要求的数据结构。
- ROW/COL、SUBFORM、关联组件和普通字段各自只提交一次。

实施方式：先抽取无副作用的序列化函数及规则矩阵，再让现有入口复用；不要在各页面继续增加同类分支。

验收：上述字段类型均有单元测试；五类提交入口使用同一序列化规则，并完成新增、草稿、重新申请和审批提交回归。

### P1：收敛应用运行时重复逻辑

`views/application/index.vue`、`manager.vue`、`visitor.vue` 重复处理应用信息、表单、流程、默认值和联动初始化，修复容易只覆盖部分入口。

- 抽取共享运行时或 composable，页面只保留模式编排。
- 通过适配器隔离接口差异。
- 明确保留 visitor 不恢复表单缓存，以及管理、普通填报在权限、按钮和默认值上的差异。
- 优先复用提交序列化和安全配置解析，避免一次性重写三个页面。

验收：三种入口的日期、隐藏字段、人员/部门、联动和草稿行为分别符合原规则。

### P1：拆分高风险大文件

当前维护风险最高的文件包括：

- `views/doCenterDes/index.vue`：约 2700 行，混合详情数据、节点操作、表单展示、流程记录和打印。
- `views/taskManageCenter/fillDetail.vue`：约 2400 行，混合任务数据、填报、导出打印和流程展示。
- `src/utils/form.ts`：约 2300 行，混合初始化、联动、校验、赋值和提交转换。
- `views/application/components/OriginalDataPanel.vue`：约 1600 行。

按“纯数据转换 → 独立副作用 → 展示组件”的顺序逐块拆分。每次只迁移一个职责，保持接口和页面行为不变；打印导出、提交序列化、流程记录适合作为首批边界。

验收：路由页面只负责参数和模块编排；抽取逻辑有测试；单次 SVN 变更可独立回退。

### P1：异步与响应式稳定性

当前快照仍有约 67 处 `setTimeout` 和 29 处深度监听。它们不都属于缺陷，但固定延时初始化、监听中回写依赖和未处理过期响应容易产生递归更新、重复请求或旧数据覆盖。

- 初始化优先使用 ready 事件、Promise、`nextTick` 或明确的加载状态。
- watcher 缩小到必要字段，避免在监听回调中无条件改写同一响应式来源。
- 搜索、树选择和联动请求处理取消或过期响应。
- 新增定时器、事件监听和 Blob URL 时同步实现清理。

验收：慢网、快速切换路由、反复打开人员/部门弹窗及流程分支弹窗时，无递归更新、重复确认或旧数据回填。

### P1：分包与重依赖治理

入口 eager 加载已修复，但生产构建仍存在大 chunk 警告，同时全局组件异步注册会产生较多小文件。Monaco、wangEditor、图表、xlsx、mammoth 等应只在对应功能真正使用时加载。

- 使用 `npm run build:analyze` 记录入口、公共包和主要路由包体。
- 检查首页、应用列表和普通详情页的实际网络请求，而非仅看源码是否动态导入。
- 按稳定依赖边界合并过小 chunk，避免为减少请求数把重依赖重新放回公共入口。
- 图片和应用图标继续使用失败回退、按需加载及稳定缓存地址。

验收：首页和普通业务页不下载非必要编辑器/文件处理依赖；现代与 legacy 构建、直接访问和刷新均正常；形成可比较的构建数据。

### P1：生产调试输出与错误可观测性

当前业务源码仍约有 141 处有效 `console.log/debug`，集中在设计器、任务填报、指标和应用更新等路径。大量调试输出既干扰排错，也可能暴露配置或表单数据。

- 删除临时 `console.log/debug`，禁止打印完整请求、表单值、令牌和动态配置。
- 必须保留的错误使用统一上报或受环境开关控制的日志工具。
- `console.error/warn` 不做机械删除，先区分用户可处理错误和开发诊断。

验收：生产构建无业务数据调试打印；关键失败仍有用户提示和可定位上下文。

### P2：依赖安全与质量门禁

- 在可访问的 npm registry 环境重新执行生产依赖审计，记录依赖、影响路径和处置结论；禁止直接使用 `npm audit fix --force`。
- 对 `expr-eval`、`xlsx` 等无法直接升级的依赖限制输入边界或评估替代方案。
- 增量引入 ESLint/Prettier，先覆盖新增和修改文件；当前仍有约 21 处废弃 `::v-deep` 语法，应随相关页面修改迁移为 `:deep()`。
- E2E 优先覆盖表单提交、审批操作、人员/部门选择、打印和连接器保存。

验收：审计结果可追踪；新增代码进入质量门禁；核心 E2E 可在两个工程重复执行。

### P2：双工程同步规则

- 公共修复按文件同步，不做整目录覆盖。
- 维护差异白名单，至少包含 `/wornbench/` 与 `/workflow/` 基路径及 DMP 专有文件。
- 每次提交分别执行两个工程的类型检查、测试和生产构建。
- SVN 提交只包含本次变更；提交说明记录同步范围、验证结果和保留差异。

验收：公共文件差异均能由白名单解释，任一工程可独立构建和部署。

## 3. 建议执行顺序

1. 在 application、审批详情和任务填报入口接入安全配置解析与结构校验。
2. 抽取统一表单提交序列化函数，补齐字段和容器规则测试。
3. 清理生产调试输出，并为关键错误保留统一诊断入口。
4. 先拆打印导出和提交转换，再逐步拆应用运行时与超大页面。
5. 执行构建分析，调整重依赖与小 chunk 边界并记录前后数据。
6. 补核心 E2E、依赖审计和 SVN 双工程提交门禁。

## 4. 每项变更完成标准

- 两个工程均通过 `vue-tsc --noEmit`、相关单元测试和生产构建。
- 核心流程完成回归，常用桌面分辨率与 2K 分辨率布局正常。
- 性能优化提供前后数据；缺陷修复提供自动化用例或明确复现与验证步骤。
- SVN diff 不包含调试输出、构建产物、无关格式化或未说明的双工程差异。
