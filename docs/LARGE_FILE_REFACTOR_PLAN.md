## 2. 拆分设计

### 2.1 组件配置：data/form.js

原路径继续导出 `formConf`、`inputComponents`。建议在 `src/data/formComponents/` 下组织配置：

| 模块 | 内容 |
| --- | --- |
| `basic.js` | 基础组件定义 |
| `advanced/` | 进阶组件，按数字金额、日期时间、人员部门、其他输入拆分 |
| `advanced/index.js` | 按现有顺序组装进阶组件 |
| `extended.js` | 当前“高级组件”分组 |
| `business.js` | 当前“业务组件”分组 |
| `layout.js` | ROW/COL 等布局定义 |
| `decoration.js` | 标题、分割线等“其他组件”定义 |

配置迁移保持对象内容、组件顺序、属性面板顺序、默认值和对象引用关系。初次迁移沿用 JS，避免同时改变配置类型推断。不要提前把重复 props 合并成共享可变对象，否则修改一个组件可能影响其他组件。

验证：迁移前后完整配置深度等价；从同一组件连续创建两份表单字段，实例修改互不影响；栅格复制后的 id 和子字段数量符合原规则。

### 2.2 表单工具：utils/form.ts

在 `src/utils/form/` 下拆分实现，原 `src/utils/form.ts` 显式转导出已有公共函数。内部模块直接引用实际实现文件，禁止经旧入口回引。

| 模块 | 迁移职责/现有函数 | 依赖约束 |
| --- | --- | --- |
| `dateFormats.ts` | `setFormat`、前后端日期格式转换、显示/提交时间格式化 | 可依赖 dayjs，不依赖页面、路由或缓存 |
| `storage.ts` | `getFormById`、`setFormById`、`clearFormById` | 保留 `formList` 键和日期格式归一化 |
| `fieldLookup.ts` | `getFormList`、`deepGetForm`、`deepGetSubForm`、`getProps`、`setProps` | 复用现有树工具；保持原查询语义 |
| `referenceData.ts` | `extractAllRelatedIds`、人员/部门分批查询 | 缓存生命周期和 Pinia store 调用方式不变 |
| `hydrate.ts` | `setUpDateData`、`setUpDateSubFormData`、`setFormData` | 保留递归互调、请求时序和回填规则 |
| `serialize.ts` | `submitFormData`、空值判定 | 复用 `walkFormFields` 和格式工具，不引入网络请求 |
| `runtime.ts` | `setForm`、`resetFormRuntimeData`、`setDefaultValue` | 管理默认值、子表实例及运行时重置 |
| `expressions.ts` | `getQuery`、`setExpressionValue`、公式请求去重 | 复用 `formSelectOptions`、`formLinkage`，保持去重 Map 生命周期 |
| `visibility.ts` | `setFieldControl`、`setFormLogics` | 保留权限、显隐、子表联动顺序 |
| `validation.ts` | `setRules`、JSON Schema 校验规则 | 依赖格式模块，不引用页面 |
| `columns.ts` | `convertToColumns`、`convertToColumn` 及单元格渲染 | 集中表格展示和附件预览；不被提交模块依赖 |

重要兼容点：

1. 当前 `submitFormData` 原地修改 `params.formData`。首批保留该接口和变更语义，不直接改成“返回新对象”而遗漏旧调用方；纯转换内核可后续在兼容包装下引入。
2. 当前公式模块从 `utils/form` 导入 `getFormById`，而 `form.ts` 导入公式计算模块。先完成 `storage.ts`，将公式侧缓存依赖指向该叶子模块，再迁移公式逻辑，避免延续或扩大循环依赖。
3. `setUpDateData`、`setUpDateSubFormData`、`setFormData` 的交叉调用先保留在同一个回填模块内。进一步拆分前，确认回填时序与副作用。
4. `getProps` 当前存在模块级临时状态。迁移时记录其兼容行为，状态污染修复另做独立变更和测试。
5. 不同时修改 `map(async ...)`、定时器和默认值规则；这些调整会改变执行时序，需要单独验收。

## 4. 验证与完成标准

测试重点是可观察行为和数据协议：

- 序列化：普通字段、ROW/COL、多层布局、SUBFORM、人员/部门单多选、日期/时间、关联字段与隐藏字段。
- 缓存/格式：旧缓存回读、保存后回读、前后端日期格式往返、配置源对象是否被意外修改。
- 导出：无模板、单模板、多模板确认/取消、请求失败、打印后再下载、已选/全部记录。
- 网格：碰撞、边界宽度、初始布局修正、拖拽后保存再打开、重做恢复。
- 页面：设计/预览/填报/审批、访客首次进入、只读状态、2K 展示以及用户已修复的下拉与间距样式。

每批运行相关测试与 `npx vue-tsc --noEmit -p tsconfig.app.json`；每个可交付批次执行全量单元测试和生产构建。当前审查曾记录 `requestHelpers.test.ts` 有 1 个失败，这不是本轮新测试结论；实施前重跑确认。如果仍失败，应单独注明基线失败，新增失败必须在本批解决，不能删测试掩盖。

代码验收：

1. 原有公共导出、接口参数、路由、缓存及权限行为兼容，未引入循环依赖或模块加载时副作用。
2. 页面组合状态保留响应性，异步回调读取最新 ref/getter；组件通过 props/emit 通信，禁止用整个页面上下文对象透传依赖。
3. 迁移的监听器、定时器、图表实例和弹窗临时状态有明确生命周期归属。
4. 样式随实际 DOM 归属迁移，确认 scoped 作用域、父子选择器和 Teleport 弹层没有变化。
5. 新增工具/composable 以 150–500 行为维护参考，页面入口以 800 行以内为方向；超过时按职责说明原因，行数不是唯一验收标准。
6. 更新拆分前后行数、模块职责及回归结果到本文件，并回填 `CURRENT_CODE_REVIEW.md` 的完成状态。

本方案完成标准是上述五个文件的职责拆分与回归交付。其他大文件，例如 `OriginalDataPanel.vue`，在本轮完成后再按相同方法评估。
