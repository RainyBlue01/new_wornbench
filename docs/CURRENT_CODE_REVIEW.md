## 2. P0：应优先修复

### 2.1 公共请求白名单为空，测试基线已失败

证据：

- `src/utils/requestHelpers.ts:1` 的 `publicRequestPrefixes` 是空数组。
- `src/utils/requestHelpers.test.ts:11-12` 明确要求主题和验证码接口属于公共接口。
- `src/utils/request.ts:95` 依赖该判断决定是否携带登录令牌。

影响：未登录阶段的主题、验证码等请求会被当作鉴权接口处理；当前单元测试已失败，说明代码与既定行为不一致。后续若公共接口返回 401，还可能触发不必要的登录跳转和本地状态清理。

建议：恢复经过确认的公共接口前缀，并将白名单作为显式常量维护；至少保留主题、验证码及登录前实际调用的接口。修复后必须保证 `requestHelpers.test.ts` 全部通过。

### 2.2 动态字段脚本缺少可信边界

证据：`src/utils/fieldScriptExecutor.ts:21-36` 通过 `AsyncFunction` 编译字符串脚本，并把 `provideState`、字段对象和整份 `formConfs` 传入执行环境。

影响：脚本可以读取或修改表单配置、触发联动方法，并能访问浏览器全局对象。只要脚本来源可被低权限用户、历史脏数据或被篡改接口影响，就存在数据破坏和前端代码执行风险。`Object.freeze` 只冻结外层 context，不能冻结其中的字段和表单对象。

建议：

1. 明确脚本只能由可信管理员配置，并在接口侧校验权限和审计变更。
2. 前端执行环境改为最小能力 API，不直接暴露完整 `provideState` 和可变表单对象。
3. 为脚本增加允许的操作清单、超时或中断策略以及执行失败隔离。
4. 增加“无权限配置、恶意脚本、脚本异常、连续触发”测试。

## 3. P1：影响稳定性和回归风险

### 3.1 栅格编辑使用不稳定 key，并假设所有节点 id 都是字符串

证据：

- `src/components/showItem/qCol.vue:6` 使用 `index + 'i'` 作为编辑态列表 key。
- `src/components/showItem/qCol.vue:70` 直接执行 `v.id.split('.')`，没有校验节点、id 和 props。
- `src/components/showItem/qCol.vue:50` 将注入结果强制断言为存在，后续直接调用方法。

影响：复制、插入、删除或拖拽栅格字段后，索引 key 会复用错误的组件实例，可能出现值、校验状态或异步选项串位。历史数据缺少 id/props 时，拖入栅格会直接报错。

建议：编辑态和预览态统一使用稳定字段 id；对 children、id、props 做结构归一化；注入缺失时提供明确降级或错误提示。补充复制栅格、同列多字段、嵌套 ROW/COL 和历史数据缺字段的测试。

### 3.2 异步下拉选项存在请求竞态

证据：`src/components/showItem/qSelect.vue:20-48` 在数据源配置变化时重复调用 `refreshSelectComponentOptions`，没有取消旧请求或校验请求序号。

影响：快速切换数据源、表单、字段或过滤条件时，较早发出的请求可能较晚返回并覆盖最新选项；多个并发请求共用一个 `loading` 布尔值，也可能提前结束加载状态。

建议：使用 `AbortController` 或递增请求序号，只接收最后一次请求结果；加载状态与当前请求绑定。增加快速切换数据源的竞态测试。

### 3.3 字段值深度监听可能放大联动更新

证据：`src/components/showItem/showItem.vue:152-158` 对每个字段值使用 `deep: true` 监听，并在回调中执行字段脚本及 `filterData`。

影响：人员多选、部门多选、子对象和数组的内部修改都可能触发整套联动；字段脚本再次修改自身或关联字段时，容易形成递归更新、重复请求或重复计算。字段数量增加后，深度依赖收集也会放大渲染成本。

建议：按字段类型监听稳定的序列化值或明确事件，不对所有字段统一深度监听；联动执行增加重入保护和变更去重。重点回归人员/部门单多选、关联字段和公式字段。

### 3.4 全局表单样式依赖大量 `!important`

证据：`src/styles/form-controls.scss:10-248` 同时提供全局、mixin 和 deep 三组表单控件规则，并大量使用 `!important`；全项目当前约有 1021 处 `!important`。

影响：组件自身尺寸、状态和预览样式难以覆盖，修复一个页面容易影响设计态、预览态或正式填报页。近期下拉框预览样式冲突已经验证了该风险。

建议：将表单外观限定在明确的容器类下，用设计 token 和状态类替代全局强制覆盖；分批移除 input/select/picker 的 `!important`，每批同步回归设计、预览、访客、审批和只读页面。

### 3.5 DMP 与经管版公共文件已出现行为漂移

当前对照结果：

- `qCol.vue`：DMP 使用 `gap: 16px`，经管版使用相邻元素 `margin-top: 16px`。
- `qSelect.vue`：DMP 默认启用 `allow-search`，经管版没有该行为。
- `seeModel.vue`、`form.ts`、`requestHelpers.ts` 等公共职责文件的哈希也不一致，需逐项确认是否属于基路径或业务差异。

影响：同一问题在两个工程表现不同，修复和验收结论不能复用；只提交一个工程会造成持续回归。

建议：建立公共文件差异白名单和自动比对脚本。SVN 提交前输出非白名单差异，公共修复必须在两个工程分别执行类型检查、测试和构建。

### 3.6 核心业务缺少自动化回归

现状：项目只有 6 个单元测试文件和 1 个登录 E2E；近期高频修改的栅格、日期格式、人员/部门选择、流程分支、打印、连接器和表单提交没有端到端保护。

影响：类型检查和构建只能证明代码可编译，无法发现提交数据遗漏、预览与正式页面不一致、异步竞态和样式覆盖。

建议按以下顺序补充最小回归集：

1. 栅格内字段新增、复制、预览和提交。
2. 日期/时间格式化及 `getDayCalculate` 边界。
3. 人员和部门单选、多选确认与回显。
4. 流程分支“为空/不为空”和节点保存。
5. 多模板打印、连接器保存及 visitor 首次进入。

## 4. P2：后续治理

### 4.1 ISO 时间解析会丢失时区语义

证据：`src/components/expression/formula/dateFormula.ts:273-274` 先删除字符串中的 `Z`，再交给 `new Date` 解析。

影响：原本表示 UTC 的 ISO 时间会被当作本地时间处理，在东八区产生 8 小时偏差；跨日时会直接影响日期差和天数公式。现有测试没有覆盖带 `Z` 和时区偏移的输入。

建议：保留标准 ISO 时区信息；只对无时区的 `YYYY-MM-DD HH:mm:ss` 做显式本地解析。补充 `Z`、`+08:00`、跨日和夏令时环境测试。

### 4.2 超大文件继续放大修改风险

当前高风险文件包括：`data/form.js` 3122 行、`doCenterDes/index.vue` 2706 行、`taskManageCenter/fillDetail.vue` 2437 行、`utils/form.ts` 2340 行、`designer/index.vue` 1790 行。

影响：页面编排、请求、数据转换、打印和状态更新混在同一文件，局部修改难以验证，双工程同步也更容易遗漏。

建议优先抽取纯函数和可测试边界：表单提交序列化、打印数据准备、流程树转换、应用运行时初始化。每次只迁移一个职责并保持接口不变。

### 4.3 生产调试输出仍可能暴露业务数据

当前业务源码约有 143 处 `console.log/debug/info`，集中在报表、任务填报、流程树、上传和表单逻辑。

影响：控制台噪声会掩盖真实错误，完整对象输出可能包含表单值、流程配置或接口响应。

建议：删除临时打印；必须保留的诊断信息统一走受环境开关控制的日志工具，只记录业务 id、错误类型和必要上下文，不记录令牌及完整表单数据。
