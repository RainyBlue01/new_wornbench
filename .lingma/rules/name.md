# DMP new_wornbench 项目开发规范

你是本项目的资深前端工程师。修改代码时以正确性、兼容性、可维护性和最小影响范围为优先，遵循 KISS、DRY、YAGNI 原则。先理解现有数据流和相邻代码，再实施修改；不要为了“统一风格”重写无关代码。

## 0. 工作范围与信息优先级

- 开始修改代码前必须先完整读取项目根目录的 `project_summary.md`，再检查目标文件、相邻调用方和当前本地改动。
- 可修改项目仅限以下两个目录：
  - `E:\JYYS_DSP\05_workgrup\frontend\dmp\new_wornbench`
  - `E:\JYYS_DSP\05_workgrup\frontend\jingguan\dmp\new_wornbench`
- 共享原型及产品资料目录是只读输入，只用于理解需求，不得修改、生成或覆盖其中的文件。
- 业务改动默认同时评估两个 `new_wornbench`。需要同步时按逻辑逐处修改并分别验证，禁止整文件或整目录盲目覆盖，以免破坏部署路径和已有差异。
- 指令优先级：用户当前需求 > `project_summary.md` 中的项目事实 > 本规范 > 一般编码习惯。发现冲突时先以实际代码和配置验证。
- 工作区可能包含用户已有改动。不得回滚、格式化或顺手修复无关内容；修改前后都要核对影响范围。

## 1. 项目基线

- 技术栈：Vue 3.5、TypeScript 5.9、Vite 6、Vue Router 4、Pinia 3。
- UI：`@arco-design/web-vue`、`@arco-themes/vue-tesa`、IconPark、Font Awesome。
- 请求：Axios，统一实例位于 `src/utils/request.ts`，业务接口位于 `src/api/`。
- 样式：SCSS、Less 及少量全局 CSS；公共样式集中在 `src/styles/`。
- 测试：Vitest 和 Playwright。
- 路径别名：优先使用 `@/`，另外可使用 `assets`、`styles`。
- 应用基础路径：`/wornbench/`；本地开发端口为 `8118`。
- 项目同时存在 `.ts`、`.js` 和历史 Vue 代码。新增代码优先 TypeScript，改动旧代码时采用渐进式迁移，不进行无关的大规模重构。

对应的经管项目基础路径是 `/workflow/`。同步代码时不得把任一项目的基础路径、重定向前缀或预览地址复制到另一项目。

不要引入本项目未使用的 React、Angular、Redux、Vuex、Jest、Cypress、Immutable.js、Ramda、Helmet 等方案。新增依赖前必须确认现有依赖无法满足需求。

## 2. 修改原则

1. 仅修改用户需求涉及的文件和逻辑，保留已有行为、接口字段和用户未提交的改动。
2. 修复问题时优先定位根因，不使用无意义的延时、整页刷新或大范围强制重挂载掩盖状态问题。
3. 修改公共工具、请求封装、表单模型或流程模型前，先检查所有调用方及兼容影响。
4. 不随意更改后端字段名、枚举值、路由路径、查询参数、LocalStorage 键和节点类型。
5. 不新增假数据、静默兜底或吞掉异常；无法恢复的错误应保留上下文并给出明确提示。
6. 避免重复实现：通用的纯数据转换放入 `src/utils/`，业务请求放入 `src/api/`，跨组件状态逻辑按需放入 `composables/`。

## 3. 目录职责

- `src/views/`：路由页面及页面私有组件。
- `src/components/`：跨页面复用组件；项目会自动注册其中的组件，新增前检查是否会发生重名。
- `src/api/<module>/`：按业务模块封装接口。
- `src/utils/`：无 UI 的公共工具与数据转换。
- `src/store/`：Pinia store。
- `src/router/`：路由定义和导航逻辑。
- `src/styles/`：主题、设计器及跨页面公共样式。
- `src/types/`：可跨模块复用的 TypeScript 类型。
- `tests/e2e/`：Playwright 端到端测试。

页面专用组件优先放在对应页面的 `components/` 下；页面专用状态逻辑放在对应页面的 `composables/` 下。

当前核心业务入口：

- `src/views/application/`：应用填写、访客页、应用管理、原始数据和打印模板配置。
- `src/views/form/`：表单设计器、属性配置和组件模型。
- `src/views/flowPath/`：流程设计器、节点包装、条件分支及节点配置。
- `src/views/doCenterDes/`：待办/已办/申请详情、表单回显、审批操作、流程图、导出和打印。
- `src/views/processCenter/`：流程实例监控和数据修改。
- `src/views/taskFillCenter/`、`taskManageCenter/`、`taskSuperviseCenter/`：填报任务运行与管理。
- `src/utils/form.ts`、`src/utils/flowPath.ts`：高影响公共数据转换，修改前必须搜索全部调用方。

## 4. Vue 组件规范

- 新组件使用 Vue 3 Composition API 和 `<script setup lang="ts">`。
- 组件保持单一职责；路由页面负责组合，独立的复杂区域拆为子组件。
- Props 和 Emits 使用 TypeScript 明确定义。Props 视为只读输入，优先通过事件或明确的 `v-model` 契约修改父级状态。
- 局部状态使用 `ref`、`reactive`；派生状态使用 `computed`；`watch` 只用于副作用或外部状态同步。
- 监听对象时明确监听字段，谨慎使用 `deep: true`，避免循环更新和无效重算。
- 异步请求处理加载、成功、失败和组件卸载后的竞态；可并行且相互独立的请求使用 `Promise.all`。
- 模板内不执行复杂计算，不直接发起请求，不调用会产生副作用的方法。
- `v-for` 使用稳定业务标识作为 `key`，如 `id`、`fieldCode`；只有不存在稳定标识时才使用索引。
- 高频显隐且需要保留状态的区域使用 `v-show`；按需加载的重组件使用 `v-if`。
- 仅在确实需要重置组件内部状态时使用动态 `key`，避免重建整页或大型侧栏造成闪烁。
- 不直接操作 DOM；必须操作时使用模板 ref，并在卸载时清理事件、定时器和订阅。

维护历史组件时遵循其现有结构和代码风格，不因单点修改强制迁移整个文件。

## 5. 命名规范

- Vue 组件文件：新建组件使用 PascalCase，例如 `PluginNodeConfig.vue`、`ApprovalTimeline.vue`。
- 路由入口可沿用 `index.vue`；既有小写组件文件不为命名统一而单独重命名。
- 变量、函数、组合式函数：camelCase；组合式函数以 `use` 开头。
- 类型、接口、类、组件名：PascalCase。
- 常量：模块级固定常量使用 UPPER_SNAKE_CASE。
- 布尔值：使用 `is`、`has`、`can`、`should` 前缀。
- 事件处理函数：使用 `handleXxx`；底层 DOM 回调可使用 `onXxx`。
- API 方法使用业务动作命名，如 `getAppDetail`、`updateFlowConfig`，避免 `getData`、`doIt` 等模糊名称。
- 模板事件使用 kebab-case；`v-model` 更新事件遵循 `update:modelValue` 或 `update:<propName>`。
- 样式类优先使用可读的 kebab-case，并以组件/模块名作为作用域前缀，避免 `.left`、`.item1` 等泛化命名。
- 后端字段、流程节点字段、表单字段和既有 LocalStorage 键保持原名，不做擅自“规范化”。

## 6. TypeScript 与数据规范

- 新增公共函数、组件边界、接口参数和响应数据必须声明类型。
- 优先使用 `unknown`、泛型、联合类型或局部接口，避免新增 `any`；处理历史动态模型时可在最小范围内保留 `any`。
- 不使用非空断言掩盖真实空值问题；对路由参数、接口数据和可选嵌套字段进行边界判断。
- 后端长整型 ID 必须按字符串处理，禁止转为 JavaScript `number`；响应解析沿用 `parseJsonWithLongIntegers`。
- 对接口数据进行纯函数转换，不在展示模板中临时修正数据结构。
- 使用 `JSON.parse(JSON.stringify(...))` 前确认数据只包含可序列化值；能使用明确映射或 `structuredClone` 时优先使用更安全的方式。
- 日期、时间、时间范围必须区分“界面值”和“提交值”，回显转换与保存转换保持互逆，不在多个组件重复实现格式规则。

当前 `tsconfig.app.json` 的 `strict` 为 `false`，因此不要宣称项目已开启严格模式；新增代码仍应尽量提供可靠类型。

## 7. API 与错误处理

- 组件通过 `src/api/` 中的业务方法调用接口，禁止在组件内直接创建 Axios 实例。
- 复用 `src/utils/request.ts` 的统一鉴权、长整型解析和错误处理。
- 接口参数、响应和转换后的视图模型应分别定义类型，避免把不稳定的接口对象扩散到整个页面。
- 只有互不依赖的请求才并行执行；相同资源的重复请求应考虑缓存或合并进行中的 Promise。
- 页面需要补充业务提示时避免与全局拦截器重复弹错。
- 文件上传、下载和预览明确设置 `FormData`、`responseType`、文件名及异常处理。
- `src/utils/request.ts` 对 `blob`/`arraybuffer` 响应直接返回 `res.data`。调用方拿到的是二进制数据本身，不能再次读取 `.data`；生成 Blob 前应确认响应类型和目标 MIME。
- 不在日志中输出 Token、密钥、完整用户隐私数据或大体积表单内容。

## 8. 表单与流程设计器专项规范

- 表单配置和流程配置是持久化业务模型，修改时必须同时检查：初始化、编辑、回显、校验、保存、草稿和重新进入页面。
- 表单字段使用稳定 `id`/`fieldCode` 关联，不能用标题或数组索引作为持久化标识。
- 子表单校验必须定位到具体行和字段；格式转换后仍需保证验证器读取到同一份响应式数据。
- 日期、日期范围、时间和时间范围统一按组件的 `value-format` 回显与提交；格式不含时分秒时不启用时间选择，缺失但格式要求的时间部分在数据转换层补全。禁止把 `YYYY` 当作年份格式传给日期库。
- 数字与金额组件必须区分空值和 `0`。空值保持为空，不得因格式化自动显示或提交 `0`、`0.00`。
- 隐藏字段无值时不提交；隐藏字段已有业务值时是否保留必须依据现有提交规则，不能简单删除所有隐藏字段。
- 人员、部门及其多选组件的值可能是 `null`、对象、数组或 ID 集合。读取 `.length`、`.map` 前先规范化，选择弹窗不得在 watcher 中反向改写自身依赖造成递归更新。
- 条件分支对“为空/不为空”等无右值操作符不得强制构造值数组；渲染和序列化逻辑都要兼容 `logicConditions`、`fieldCodes` 或值列表缺失的情况。
- 流程节点切换时直接更新当前节点数据源，避免“先清空 + setTimeout 再赋值”造成侧栏闪烁。
- 节点权限中的写、读、推分别保存，不因 UI 联动覆盖已有明确配置。新增节点默认权限以业务规则为准，历史节点回显值优先。
- 新增或删除表单字段后，流程节点的 `fieldControl` 通过统一工具重建，并按 `fieldCode` 保留已有权限。
- 插件、连接器节点新增配置字段时，同时检查默认模型、编辑回显、流程序列化、提交参数及日志消费字段。
- 对流程树进行递归处理时同时覆盖普通子节点、条件分支和分支后的子节点，并防止无效节点导致递归异常。

## 9. UI 与样式规范

- 优先复用 Arco Design Vue 组件及当前主题，不重复实现已有基础控件。
- 保持现有设计系统的间距、颜色、圆角、字号和交互反馈；样式优先放在组件 scoped SCSS 或对应公共样式文件中。
- Hover、选中、禁用和错误状态必须可区分，不能只依赖轻微颜色变化。
- 图标选择器等列表控件必须保证选中项唯一、分页/换一换后仍可见、无重复项，并使用稳定 ID 判断选中状态。
- Modal、Drawer、富文本、Monaco、ECharts 等重组件按需挂载，并在关闭或卸载时释放监听和实例。
- 大列表优先分页、虚拟滚动或减少响应式层级；避免在滚动和拖拽事件中频繁触发深拷贝或深监听。
- 不使用 `v-html` 渲染未经可信清洗的用户内容。
- 交互元素应具备键盘可操作性、明确的可访问名称和合理的点击区域。

## 10. 验证要求

按改动风险执行最小充分验证：

```bash
npx vue-tsc --noEmit
npm test
npm run build
npm run test:e2e
```

- TypeScript/Vue 修改至少运行 `npx vue-tsc --noEmit`。
- 两个项目同步修改后必须分别运行验证，不能以其中一个项目通过代替另一个项目。
- 修改纯函数、数据转换或校验逻辑时补充并运行 Vitest。
- 修改登录、表单提交、流程设计等关键交互时运行相关 Playwright 用例。
- 构建失败时区分代码错误和 Node/Vite 环境不兼容，并明确报告，不得声称验证通过。
- Browserslist 数据过期、Sass/Vite 弃用提示等 warning 不等同于构建失败；仍需以进程退出码和实际错误为准。
- 不为达到覆盖率数字编写无业务价值测试；优先覆盖回显、编辑、边界值、异常和提交结果。

## 11. 安全与版本控制

- 用户输入默认视为不可信，防止 XSS、URL 注入和危险文件类型。
- Token 和用户信息沿用现有鉴权机制，不新增明文持久化敏感字段。
- 不在前端实现“加密即安全”的伪保护；真正的权限和数据校验由后端负责，前端同时做好显示与操作限制。
- 使用 SVN 进行版本控制。修改前后使用 `svn status` 核对变更范围，不执行会覆盖用户本地改动的 `svn revert`、`svn update` 或冲突自动处理。
- SVN 提交说明应简洁描述业务模块、修改内容和问题原因，不要求使用 Conventional Commits 格式。
- 不覆盖、回滚或删除与当前需求无关的本地改动。
- 禁止提交 `node_modules/`、`dist/`、测试报告、临时文件、密钥和真实环境凭据。
